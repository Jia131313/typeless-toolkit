# Windows 安装版、更新交接与 Node 环境方案

日期：2026-10-09。状态：源码已推送功能分支，GitHub Windows/Mac 构建及既有包检查成功，两个 Setup 已取回。未合并或发布，未替换真机安装；G15 交互验收未完成。

## 原始需求与已确认决定

- 用户反馈 Windows ZIP 自更新没有可靠的成功体验：下载后无明显后续动作，有时下载失败、有时校验失败，不能判断替换是否成功。后续 G15 只读现场检查已确认当前检查失败为 GitHub API 限流，并复现 PowerShell 编码缺陷；历史下载/校验失败仍缺原始记录。
- 用户希望增加安装版，确认同时提供 Lite 和内置 Node 两种，接受未知发布者；暂不采购代码签名证书。
- 用户接受暂时保留 Lite/Portable ZIP；先做安装版，安装版验收稳定后再讨论取消 ZIP 自替换，不直接取消 ZIP 或强制迁移。
- 用户担心官网安装的 Node 不会自动更新，导致 Lite 功能不兼容；需明确环境维护责任、能力要求与提示。
- 用户随后明确要求“开始实现”，并在讨论后确认执行 Mac 开发 → GitHub 构建 → G15 验收路线；现已授权修正既有版本断言、推送功能分支并手动触发只构建不发布的工作流。仍不授权合并、Release 或替换 G15 当前安装。

## 实施前代码事实

- 集成基线为 v1.9.3 后的 origin/main；复用现有 Windows WebView2 宿主、Node 后端和 manager.html，不重写业务界面。
- main.cs 当前将数据定位到程序目录的 data，并向后端传递路径；安装版独立数据目录需要统一修改配置读取、日志、WebView2 配置目录等引用，不能只改后端一个路径。
- lib/toolkit-update.js 当前根据程序目录及同级 data 检测 ZIP 发行版，按 Lite/Portable 选 ZIP；安装版必须有明确的安装模式元数据及自己的附件选择、启动安装程序路径。
- Windows Lite 已优先探测可 require('node:sqlite') 的 Node，再保留不具备能力时的基本运行选项；现有实现未在选择时完整验证基本最低版本。安装版应将版本与能力检查统一复用，避免安装器、宿主、UI 各判一遍且口径不同。
- 基本运行要求文档为 Node 22.12+；SQLite 能力不能简单写成“必须 Node 23.4+”，较新的 Node 22 也可具备该能力。自动切号还取决于 Typeless 数据库能否读取，不是 Node 有 SQLite 就一定可用。
- 官网 Windows Node 安装程序不负责自动更新；包管理器升级也需用户执行或另行配置。Lite 不应自行覆盖系统 Node 或修改系统 PATH。

## G15 现场发现与处理计划

2026-10-09，经已配置的 Tailscale SSH 只读检查，无 computer use、无更新安装、无进程退出、无数据修改。

- 现场工具集为 1.9.3 Lite；EXE 启动自己的 Node 后端，实际 Node 为 22.23.1，来自本机 Hermes 目录。运行时来源不等同 Node 官方安装目录，不因路径特殊而判断异常。

- G15 为 Windows PowerShell 5.1。未指定编码读取 UTF-8 的 server/package.json 时中文乱码、JSON 解析失败；显式 UTF-8 读取同一文件成功并识别 1.9.3。安装后的 ZIP 更新脚本两处读取版本文件未指定编码。该缺陷可导致安装校验失败，但不能据此断言每次历史替换失败都由它造成。
- 未发现 toolkit-update-result.json；现有证据不足以还原历史下载失败、SHA-256 失败与安装尝试。后续取得原始错误后按阶段继续定位，不反复触发真实更新作为排查手段。

本轮追加任务，优先于安装版结构改动：

1. 修正 ZIP 更新器所有相关版本文件读取的 UTF-8 编码，保持 ZIP 的自替换方式不变；不能只让新安装版绕开已知缺陷。直接在 PowerShell 5.1 核对现有中文 package.json 的版本解析，不碰真实安装。
2. GitHub 限流错误读取响应原因及限流头，显示准确的原因和可重试时间；限流期间不重复请求。缓存成功的版本检查结果，避免页面进入/聚焦等触发不必要查询；缓存仍需标注检查时间，不能冒充实时结果。
3. 超时、缓存有效期等参数统一放根目录参数文件。保留明确手动重试；不嵌入个人 GitHub Token、不要求普通用户配置 Token、不新增代理服务。
4. 失败记录覆盖检查、下载、校验、安装交接与安装结果，保留原始错误类别且不含凭证。当前限流不是校验错误；安装包形式也不能消除版本查询限流。

## 首轮实现范围

### 发行形式与命名

- Windows x64 使用 Inno Setup 构建当前用户安装版，默认不要求管理员权限；不做全用户安装或 MSI。
- 对外用“安装版（内置 Node）”与“安装版（Lite）”，避免把安装版称为 Portable。
- 保留现有两个 ZIP；安装版推荐内置 Node，Lite 面向愿意维护本机环境的用户。用户 G15 使用 Lite。
- edition 表示 Lite/内置 Node，distribution 表示安装版/便携版；两者分开，不通过文件体积或目录偶然存在某文件来推断安装模式。
- 安装器身份与目标程序目录在两个 edition 间保持一致，手动换类型不产生第二套应用；更新只能匹配当前 edition，不隐式换类型。
- 重要构建参数集中到根目录 windows-build.json，版本取 package.json。复用现有公开构建入口，不另建自用目录打包路径。

### 程序与数据

- 安装程序默认使用当前用户 LocalAppData 下的 Programs 目录；用户数据使用 LocalAppData 下独立的工具集数据目录。具体名称由根目录构建参数统一生成。
- ZIP 继续使用其原目录的 data；Mac 当前路径和运行方式不变。
- 通过安装模式元数据统一解析数据目录。新路径传递优先复用命令行运行参数，不新增环境变量参数注入。
- 安装和升级仅部署程序及默认模板；已有账号、主词库、配置、快照与同步运行记录不由安装器覆盖。
- 卸载只删除程序和快捷方式，默认保留用户数据；不加入清空数据选项。

### 旧 ZIP 数据迁移

- 用户主动选择旧 ZIP 工具集目录；展示来源、目标及账号/词库概况，确认后迁移。无扫描整盘、无自动切换安装方式。
- 首轮迁移限定目标尚无业务数据的首次安装场景；已有安装数据时使用现有备份导入，不增加第二套冲突合并实现。
- 两个工具集都完整退出后，迁入账号、主词库、必要配置、登录快照和同步运行记录；配置中的路径按实际目标处理。同步内部记录不是导出备份内容，但本机迁移需保留其协调作用。
- 不搬运历史 backups、Typeless 本体回滚副本、日志、缓存和临时更新包，不生成新的全量回滚副本。开始前统计待迁入文件及体积。
- 不删除旧目录；迁移确认后再检查新安装能读取数据。旧目录的清理由用户在确认后决定，本轮不自动清理。

### Node 维护策略

- 内置 Node：使用项目固定并验证的 Node 24 LTS，由工具集发行包一起维护；不使用系统 Node，不自行追踪最新 Node。
- Lite：不下载、安装、覆盖系统 Node，不更改 PATH；推荐 Node 24 LTS，基本最低要求继续区分为 Node 22.12+。
- 统一探测候选 Node 的路径、版本、基本运行资格和 SQLite 能力。按明确规则选择可运行且具备 SQLite 的候选；没有该能力但满足基本要求时，可保留基本功能，并明确提示限制；基本要求也不满足时不能显示“环境正常”。
- 安装前呈现 Lite 环境检查结果，启动时由同一探测逻辑重新确认；不把未知发布者、WebView2 缺失与 Node 问题混为一个错误。
- UI 显示实际使用的 Node 路径、版本、来源与 SQLite 能力；推荐升级官方 LTS或改用内置 Node 版，不声称 Node 自动更新。
- 自动切号依次区分运行时不支持 SQLite、数据库缺失/不能读取、听写状态未知；不以版本号推断全部功能可用，不绕过正在听写时禁止切换的现有行为。

### 安装版更新交接

- 流程：检查 Release → 下载当前 edition 的安装包 → 校验 → 用户点击“退出并安装”并确认 → 启动可见安装程序 → 完整退出工具集 → 安装完成后重新打开。
- 安装程序仅等待/关闭工具集及其拥有的后端，不退出 Typeless 本体、不结束其他 Node 进程；不能在旧程序仍运行时直接覆盖。
- 安装版不走旧 PowerShell ZIP 替换逻辑。ZIP 首轮保留自替换机制，但修复已确认的编码错误并使用改进后的公共下载/错误反馈；后续是否转成手动更新是独立决定。
- 下载失败与安装失败分开处理；复用现有校验，不另建 checksum 机制。展示检查、下载、校验、待安装、安装交接与安装结果，不能把收到全部字节当作安装完成。
- 记录失败阶段、版本、HTTP/系统错误及实际安装结果，日志不含账号凭证。控制下载超时参数放根目录参数文件；首轮提供明确手动重试，不增加断点续传或永久后台更新服务。
- 宿主退出交接和新版本启动使用可观测的结果记录；下载成功、安装器启动成功均不单独作为更新成功证据。取消安装保持旧版可用。

## 实施顺序

1. 已知问题：先修 ZIP 更新器 UTF-8 读取，完善 GitHub 限流、查询缓存与阶段错误记录；不触发 G15 真实更新。
2. 参数与模式：统一根目录 Windows 构建参数、发行元数据和数据路径解析；保留便携与 Mac 原路径。
3. 环境：复用并扩展 Node 探测，统一安装前、启动及 UI 口径，修正文档的基本/完整功能要求。
4. 安装包：复用公开构建产物生成两个 Setup，接入 Windows CI；不发布。
5. 迁移：新增明确的旧目录迁移入口，复用数据读取和现有备份导入；不复制历史大备份。
6. 更新：按安装模式选附件，安装版交接给可见安装器，加入可排查结果；保留 ZIP 自动更新机制。
7. 验证与交付：现有检查、Windows CI 编译和安装器直接运行；提供验收产物，在 G15 完成一次真实旧版→新版升级，再按用户明确授权推进 PR/合并/发布。

## 验收标准

- 两种 Setup 可当前用户安装，无新增管理员要求；Lite 不含 Node，内置版使用包内 Node；入口仍只有 TypelessToolkit.exe。
- Lite 的无 Node、低于基本要求、满足基本要求但无 SQLite、有可用 SQLite、存在多个 Node 候选分别给出真实结果；不修改系统 Node。
- 旧 ZIP 数据迁入后，账号、词库及必要配置能读取，旧目录不删除，无历史大备份复制；安装版更新及卸载不删除业务数据。
- 可见更新交接完整退出工具集；新进程版本符合目标、数据仍可用才确认升级成功。取消、文件占用或安装失败有明确结果，不宣称 Inno Setup 自动提供完整回滚。
- 首轮 ZIP 与 Mac 的选包和路径不变，不隐式转换安装模式或 edition。
- PowerShell 5.1 能正确读取 UTF-8 中文版本文件；GitHub 限流明确显示原因及重试时间，等待期不重复发请求；其他下载/校验错误不错误归因于限流。
- G15 验证首次安装、迁移、托盘/单实例、Lite Node 选择、一次版本升级及取消安装。CI 包成功不代替真机交互验收。
- 使用现有检查和直接运行，不新增测试文件、通用护栏或无关功能；涉及 UI 时遵循 DESIGN.md。
