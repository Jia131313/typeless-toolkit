# 管理页交互与数据逻辑优化方案

日期：2026-11-18。状态：方案已出，待实施；用户已决定交由其他 agent 执行。
基线：`origin/main` 的 `cf1a5b3`（含 PR #67 根目录整理、PR #68 弹窗补丁 EBUSY 修复，均未发布，当前最新 Release 为 v2.2.0）。
调研环境：Windows 11、Typeless 2.12.0、本机自用安装版 2.2.0（已含 PR #68 修复）、2 个账号。

## 1. 开工前必读

1. 完整阅读 `AGENTS.md`、`README.md`、`docs/DESIGN.md`、`docs/LOCALIZATION.md`；如存在未跟踪的 `LOCAL_DEVELOPMENT.md` 也要读。
2. **设计历史红线**（`docs/DESIGN.md` 的 “Local layout demo — 2026-09-08”）：用户曾否决一次整体改版（“我感觉你改远了，还不如现在的版本”），并要求“前端这块别越改越难看了”。本方案只做定点修正：
   - 保留现有布局、蓝色主题与明暗主题变量、账号卡片结构（340px 最小列宽的自动网格）、首页五个常用操作、四个设置分类。
   - 不隐藏常用操作，不做仅悬停可见的操作，不引入框架或新依赖，不新建并行的组件/样式体系。
   - 保留现有控件 ID、API 路径与请求体；新增字段只做向后兼容的追加。
3. **多语言**：界面文字必须走 `i18nText(key, 中文兜底, values)` / `__I18N(key)__`。新增或修改的每个键要同时写进 `locales/` 下全部 9 个语言文件（`zh-CN` 为源；`zh-TW` 必须是繁体且不能与简体完全相同；非中日韩语言不能含汉字；`{p0}` 等占位符保持一致）。`test/i18n.test.js` 会校验，键名沿用现有 `ui.<12 位十六进制>` 格式。
4. **测试写法**：`manager.html` 内的函数沿用 `test/manager-batch-accounts.test.js` 的方式，用 `extractFunction(name)` 抽出后在 `vm` 里运行；后端逻辑优先抽成可注入依赖的纯函数（参考 `lib/common.js` 的 `stopTypelessForFileWrite`）。
5. **隐私**：跟踪文件和截图说明里不得出现真实账号邮箱、user_id、词库词条、个人路径。验证一律用隔离示例数据（参考 `docs/DESIGN.md` 里的 fixture 做法）。

## 2. 调研证据（2026-11-18 实测）

- 首页 1200px 与 880px 布局无横向溢出、无遮挡；问题集中在数字不对、状态区杂乱、操作过程反馈弱。
- `/api/accounts` 完整查询耗时 1.3–4.5 秒（2 个账号）；直接请求 `api.typeless.com` 首字节约 2.1 秒，主要是网络往返，代码侧已并发（`manager.js:1042` 按账号并发，`lib/common.js:1574` `createLiveStatus` 内 4 个请求 `Promise.all`）。其余状态接口均为 1–3ms。
- 前端定时轮询：`manager.html:3046-3052`（当前账号 20s、词库状态 12s、跨设备同步 20s、额度 10s、弹窗维护 4s），另有 `:1154` 500ms 的本地 `tick`。窗口收到托盘后仍在轮询。
- 主词库计数 52，两个账号各 48，但状态显示“全部对齐”：只读比对确认两个账号都不缺词，差额来自主词库内 3 组大小写变体（共 4 条多余），Typeless 按不区分大小写去重。

## 3. 任务清单

按批次独立交付（见第 5 节），批次内按编号顺序做。每项写清问题、位置、改法与验收。

### 批次 1：数据与逻辑错误（优先；小改动，可随 PR #68 一起发 2.2.1）

**1.1 首页“已知额度剩”算错**
- 问题：`manager.html:1390`（`renderStats`）用 `Math.max(0, 总额度 - 总已用)`。超额账号的超出部分会抵扣其他账号余量。实测两账号 1,090/2,000 与 2,404/2,000，显示剩 506，实际应为 910。
- 改法：抽出纯函数（如 `summarizeQuota(accounts)`），剩余 = 各已知账号 `max(0, limit - used)` 之和；“已用 / 总额度”的展示保持不变。
- 验收：vm 单测覆盖正常、单账号超额、全部超额、部分账号额度未知四种情况。

**1.2 “词库合计”数字无意义**
- 问题：同一处把各账号词条数相加（96），对齐后各账号词条相同，相加没有含义。
- 改法：这张统计卡改为显示主词库条数（去重后）与对齐情况，例如“主词库 48 词 / 2/2 已对齐”，数据取自 `/api/dictionary-sync/status` 的 `summary`；点击打开现有的 `openDictionarySyncStatus()`。四张统计卡的布局与尺寸不变。
- 验收：对齐、部分失败、0 账号三种状态文案正确；1200/880px 不换行溢出。

**1.3 主词库内大小写重复**
- 问题：主词库允许仅大小写/空格不同的重复条目，导致计数 52 与账号 48 不一致，用户会误以为没对齐。
- 改法：`POST /api/master`（`manager.js:1684`）与 `saveMaster()`（`manager.html:2718`）保存前按 `trim().toLowerCase()` 去重，保留首次出现的写法；返回被合并的条目，前端提示“已合并 N 个仅大小写不同的重复词”。`readMaster()` 返回的计数也按去重后计算。读取现有主词库时不得静默改写文件，只在用户保存时生效。
- 待用户确认：保留哪种写法。默认按“首次出现”，如用户另有要求再调整。
- 验收：后端单测覆盖大小写、首尾空格、全角半角不处理（只做大小写与首尾空格）；不影响现有“删除超过 500 条拒绝”的保护。

**1.4 主词库保存前预览变更**（风险最高）
- 问题：主词库是纯文本框，删掉一行点保存就会把该词从所有账号删除（弹窗说明里有写，但保存时不提示具体删了什么）。
- 改法：`saveMaster()` 保存前对比当前主词库，弹出确认：“将新增 N 个、删除 M 个；删除会同步到所有已管理账号”，并列出将删除的词（最多显示前 20 个，其余显示“等 X 个”）。无删除时只有新增可直接保存，或沿用一次轻量确认，保持一致即可。复用现有 `appConfirm`。
- 验收：vm 单测覆盖仅新增、仅删除、同时增删、无变化（不发请求）。

**1.5 词库部分失败时说明是哪个账号、什么原因**
- 问题：`lib/common.js:1874` 的 `syncAllAccounts` 已产出每个账号的 `results`（含 `error`、`aligned`、`msg`），但 `manager.js:229` 写入状态时只保留了 `summary`，弹窗只能显示“1/2”。
- 改法：状态里追加 `failures: [{ user_id, nickname, email, reason }]`（只放未对齐的账号，原因取 `error || msg`，复用 `describeApiError` 风格的截断）。`renderDictionarySyncStatus()`（`manager.html:1639`）在 partial/error 时列出失败账号与原因；“立即检查”保持现有行为。不新增按账号单独重试的接口，除非现有 `/api/accounts/:id/sync`（`manager.js:1604`）可直接复用。
- 验收：单测覆盖全部对齐、部分失败、全部失败；文案多语言齐全。

**1.6 Windows 静默切换的启动时序**（低优先级，可放到批次 2）
- 问题：`withSilentLaunch`（`lib/common.js:318`）临时把 Typeless 的 `launchAtSystemStartup` 设为 true，启动后在 `finally` 里立即恢复。Windows 的 `win.launchApp`（`lib/platform.js:408`，经 `spawnDetachedSafe`）只把启动交给 PowerShell 就返回，设置会在 Typeless 读取之前被恢复，静默切换实际不生效、窗口仍会弹出。仅影响 `launchAtSystemStartup` 原本为 false 的用户（调研机器为 true，不受影响）。PR #68 已修复同一根因导致的补丁 EBUSY，那次只加固了补丁流程。
- 改法：Windows 启动改为等待 PowerShell `Start-Process` 返回（现成的 `spawnDetachedChecked`，必须加超时，避免 PowerShell 卡住时切号流程挂起）；`withSilentLaunch` 在确认 Typeless 进程已出现后再等一个短暂间隔才恢复设置。macOS 分支不改。
- 验收：单测覆盖“启动后才恢复”的顺序与超时路径；真机验证需要临时把 `launchAtSystemStartup` 改为 false，**必须先征得用户同意并在结束后恢复原值**。

### 批次 2：首页交互

**2.1 批量操作栏按需出现**
- 问题：`manager.html:527-528` 一带的“已选 0 · 失效 0 / 选择失效 / 清除所选 / 清除失效账号”常驻且多为禁用，“清除失效账号”在失效为 0 时仍是红色。
- 改法：仅当已勾选账号或存在失效账号时显示这一行；“选择失效”“清除失效账号”仅在失效数 > 0 时出现；勾选框保持常驻可见（不做悬停才出现）。保留现有函数与 ID（`selectBrokenAccounts`、`clearSelectedAccounts`、`clearBrokenAccounts`、`#clearSelectedBtn`、`#clearBrokenBtn`）。
- 验收：0 选中且 0 失效时整行不占位；有失效账号时出现；勾选后出现；现有 `test/manager-batch-accounts.test.js` 通过。

**2.2 当前账号卡片的“重新切换”**
- 问题：`manager.html:1573` 对当前账号显示“重新切换”，语义不清。
- 改法：当前账号卡片的按钮位改为不可点的“使用中”状态（保持同尺寸，避免卡片布局跳动）；原“重新切换”的修复用途移到账号详情底部（`openDetail`，`manager.html:1580`），仅当前账号显示，文案如“重新应用登录”，确认文案说明会重启 Typeless。
- 验收：当前/非当前账号按钮正确；详情里的重新应用仍调用原 `switchTo`。

**2.3 切换过程的卡片级反馈**
- 问题：`switchTo()`（`manager.html:1928`）只有确认框和一闪而过的 toast，切换期间其他卡片仍可点击。
- 改法：切换进行中在目标卡片显示“切换中…”并禁用所有卡片的切换按钮；完成后刷新当前账号与卡片高亮；失败时卡片恢复并保留错误 toast。`activateAccount()`（`:1945`，“在此设备启用”）同样处理。
- 验收：vm 单测覆盖进行中禁用、成功恢复、失败恢复；不能出现两个切换请求并发。

**2.4 首屏直接显示上次数字**
- 问题：`loadAccounts()`（`manager.html:1400`）先用 `?quick=1` 画卡片，但 quick 不含额度/词库/个性化，数字要等完整查询（1.3–4.5 秒）。
- 改法：后端在内存缓存每个账号最近一次完整 `liveStatus` 结果与时间；`?quick=1` 时若有缓存则一并返回，并带 `live_cached_at`。前端先显示缓存数字并标注“x 分钟前”，完整结果回来后静默替换；“刷新”按钮在请求中显示加载态，完成后显示“更新于 hh:mm”。缓存只在内存，不落盘；账号被删除或凭证更新时清除对应缓存。
- 验收：后端单测覆盖有缓存、无缓存、账号删除后失效；不改变完整查询的并发与错误处理。

**2.5 隐藏到托盘时暂停轮询**
- 改法：前端监听 `visibilitychange`，隐藏时暂停 `manager.html:3046-3052` 的定时轮询，重新可见时立即各刷新一次再恢复。
- 必须核实：Windows 宿主收到托盘时 WebView2 的 `document.hidden` 是否真的变为 true。若不会，需要在 `windows/main.cs` 隐藏窗口时设置 `CoreWebView2Controller.IsVisible = false`，显示时恢复（C# 需兼容 .NET Framework 4.x 的 `csc.exe`，改完运行 `build/build-tray.bat`）。macOS Tauri 宿主同样核实，无法验证时只做前端部分并在 PR 里注明。
- 验收：隐藏期间后端访问日志无轮询请求；恢复后状态立刻更新；额度监控、自动切号由后端负责，不受前端暂停影响（需确认）。

**2.6 键盘可达**
- 问题：账号卡片（`div.card` + `onclick`）与 `#curPill`（`div` + `onclick`）无法用键盘操作，不符合 `docs/DESIGN.md` 的可访问性要求。
- 改法：`#curPill` 改为原生 `button`，保持现有样式；卡片内的账号名改为打开详情的原生按钮（不要把整张卡片设成 `role=button`，卡片里本身还有按钮和勾选框），鼠标点击卡片空白处打开详情的行为保留。
- 验收：Tab 可依次到达状态区、工具栏、卡片名称与卡片按钮；回车/空格可用；焦点可见。

### 批次 3：弹窗与设置

**3.1 账号详情词库列表减负**
- 现状：`renderDict()`（`manager.html:1601`）每行都有“手动 / en-US”标签与红色“删除”。删除已有确认框并说明会同步删除（`delWord`，`:1627`），不需要再加撤销。
- 改法：标签只在与默认值不同时显示；“删除”改为中性色的小按钮，悬停/聚焦时再显示危险色（按钮本身常驻可见）；词库页签标题显示词条数。
- 验收：长词、大量词条下行高一致；880px 不溢出。

**3.2 主词库编辑器补充**
- 改法：在现有文本框上方加筛选框（只用于定位，不改变保存内容）、实时条数统计（去重后），并标出大小写重复的行或在下方列出。与 1.3、1.4 配合，保存流程以 1.4 为准。
- 验收：大文本（≥500 行）输入不卡顿。

**3.3 设置 → 通用：未保存提示**
- 背景：语言、主题即时生效；额度提醒需点“保存设置”。`docs/DESIGN.md` 的 2026-09-29 规范已决定额度提醒保留统一保存，**不要改成即时保存**。
- 改法：额度提醒区有未保存修改时，在保存按钮旁显示“有未保存的修改”，保存按钮切换为强调态；离开设置页或切换分类时若有未保存修改，弹出确认。
- 验收：修改后提示出现、保存后消失、撤回修改后消失；`test/manager-settings-ui.test.js`、`test/quota-monitor-ui.test.js` 通过。

**3.4 设置 → 同步与数据：关闭时收起**
- 问题：`#accountSyncProvider`（`manager.html:626`）为“关闭同步”时，整套 WebDAV 表单仍展开显示（灰色），且“账号凭证”开关看起来是绿色开启。
- 改法：关闭同步时只显示“同步服务”选择行与一句说明，其余字段与三个保存按钮收起；同步内容开关在未启用同步时显示为禁用灰态。选择服务后恢复现有表单。遵守 `docs/DESIGN.md` 2026-09-29 的设置页规范（同卡展开、开关整行布局、禁用要说明原因）。
- 验收：关闭/坚果云/其他 WebDAV 三种状态切换正常，已填写的值不丢失，保存请求体不变。

**3.5 设置 → 关于与更新：顺序调整**
- 改法：`#settings-updates`（`manager.html:686`）里把“Typeless 工具集”更新卡片放在首位，“Node 运行环境”折叠卡片移到其后。macOS 的 Typeless 本体更新卡片位置按同一原则（用户常用的在前）。
- 验收：Windows 与 macOS 两种平台条件下顺序正确。

## 5. 交付流程

1. 每个批次从最新 `origin/main` 开分支（如 `fix/ui-batch1-data-logic`），提交信息遵守用户规则：`类型: 描述`，全中文，不超过 15 字，类型为 新增/修复/优化/重构/移除。
2. 完成后先部署到用户本机自用安装版试用（安装位置向用户确认；替换前备份原文件，安装版的 `server/` 内容需与分支对应文件一致；重启时要同时结束宿主进程和它启动的 Node 后端，否则新宿主会复用旧后端）。
3. 用户试用确认后再推送、开 PR、合并；**未经用户明确同意不推送、不合并、不发布**。
4. 版本：本方案全部属于修复与体验优化，按 `AGENTS.md` 使用 patch 版本（2.2.1、2.2.2…），不升 minor。发布前统一 package、程序集、脚本文件名与标签版本；`CHANGELOG.md` 写入“未发布”段落，发布时再定日期。
5. 每个批次结束后，在本文件末尾追加“实施记录”：做了什么、验证结果、未完成项与用户反馈。
