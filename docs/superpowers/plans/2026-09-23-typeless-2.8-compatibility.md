# Typeless 2.8.0 兼容性修复计划

## 原始需求与反馈

- 工具集 1.8.1 更新后，Typeless 2.8.0 的自动弹窗维护进入“待重试”；手动重试报“可执行文件里找不到旧整头 hash”。
- 本次不能只为一个版本增加硬编码分支，需要检查新版还有哪些不兼容，并按实际结构做可持续的兼容修复。
- 新 PR #31 需要独立严肃审核，不能因无冲突直接合并；该 PR 处理 API 请求签名提取，与弹窗完整性错误不是同一链路。

## 已确认事实

- 本机工具集为 1.8.1，Typeless 为 2.8.0（2.8.0.129，arm64）。
- 弹窗 handler 能通过语义定位到 `dist/renderer/static/js/CL10drSX.mjs`，两处等长替换也能自动推导。
- Typeless 2.8.0 将 `app.asar` 的整头 SHA-256 存在 `Contents/Info.plist` 的 `ElectronAsarIntegrity` 中；主可执行文件内没有该 hash。
- 当前 `@electron/fuses` 在这份 Electron Framework 中找不到 fuse sentinel，旧实现随后错误假定 hash 一定位于可执行文件。
- 当前工具集从 Typeless 2.8.0 提取 API 签名参数失败：`未能在主进程 bundle 中定位签名参数声明`。
- PR #31 的合成夹具和常规检查通过，但对本机真实 2.8.0 `app.asar` 的提取验证失败；它最多证明兼容作者实测的 2.7.0.126 内联格式。

## 约束

- 不按 Typeless 版本号硬编码兼容逻辑，以当前 App 的真实结构和能力探测为准。
- 优先保留 Electron 的完整性校验，不把关闭 fuse 作为 macOS 默认路径。
- 正式 Typeless.app 只在 staging 候选完成内部 hash、外部完整性元数据和代码签名验证后替换；失败沿用现有完整 App 回滚。
- 不修改或覆盖账号、profiles、词库、WebDAV 配置与 `config.local.json`。
- 不触碰未跟踪的 `output/` 与 `docs/plans/v1.9.0-quota-guard-plan.md`。
- PR #31 在完成真实兼容性判断前不合并、不关闭、不回复。

## 问题拆分

### A. 弹窗补丁完整性链路

1. 将目标 handler 定位、ASAR 内容修改、外部完整性同步和代码签名拆成明确阶段。
2. 在修改前只读探测当前 App 的完整性提供方：
   - macOS `Info.plist/ElectronAsarIntegrity`；
   - Electron fuse 状态；
   - 旧版可执行文件内嵌 header hash；
   - 无完整性约束或未知格式。
3. macOS 存在 `ElectronAsarIntegrity` 时更新其 `Resources/app.asar` hash，保留完整性校验；只有实际检测到旧格式时才走旧替换路径。
4. 未知结构返回明确的不兼容状态，不进入自动重试循环。

### B. Typeless 2.8.0 API 签名

1. 分析真实 2.8.0 主进程 bundle 中签名 header 构造、字符串池和版本来源。
2. 平台和版本优先从操作系统/App 元数据取得，不依赖混淆字符串池的相邻声明。
3. 密钥提取由稳定的 header 构造语义反向定位，保留 2.7 已知格式作为兼容解析器，但不继续堆版本号特判。
4. 提取失败时不静默伪装为普通业务失败；在 `/api/env` 和相关状态中暴露具体原因。
5. Typeless 的 App/ASAR 指纹变化后允许重新提取，避免失败结果在整个进程生命周期永久缓存。

### C. 其他新版兼容性审计

- 账号当前态与长期凭证刷新。
- 额度、词库列表、词库写入与分页接口。
- CDP 收录账号、跳过教程、切换账号和设备重置所依赖的数据路径与 IPC 结构。
- macOS App 路径、启动方式、权限主体、签名和官方更新后的自动维护。
- UI 对永久不兼容、临时占用和权限问题的状态区分。

## 实施顺序

1. 只读采集 2.8.0 App 元数据、ASAR 结构和现有工具集各能力状态。
2. 形成兼容性矩阵，确定实际失效范围与不需要修改的链路。
3. 实现版本无关的完整性提供方探测与 `Info.plist` 同步。
4. 实现 2.8.0 API 签名语义提取、状态暴露与缓存失效。
5. 运行现有 `npm run check`，在隔离 staging 副本上验证补丁、完整性和签名，不先替换正式 App。
6. 隔离验证通过后，在现有完整 App 回滚机制下验证正式安装、启动、账号/额度/词库与弹窗维护。
7. 更新版本与发布说明为 1.8.2，提交清晰的兼容性 PR；经验收后再合并和发布。

## 验收标准

- Typeless 2.8.0 的弹窗补丁不再搜索不存在的二进制 hash；修改后的 ASAR、`ElectronAsarIntegrity` 和代码签名相互一致。
- 补丁后的 Typeless 能通过严格签名校验并正常启动；失败时恢复原 App。
- API 签名状态在 2.8.0 上为可用，账号额度和词库接口恢复；若未来结构未知，UI 显示准确原因而不是官方英文透传。
- 结构不兼容不会显示成可无限重试的临时状态。
- 已保存账号、快照、词库和配置前后保持不变。
- PR #31 的 2.7 格式兼容价值被保留或明确反馈，但不以牺牲 2.8 当前版本为代价。

## 本轮实现与验证记录

- API 签名缓存改为跟随 `app.asar` 的文件指纹失效；Typeless 更新后无需重启工具集即可重新提取。
- `/api/env` 在 Windows 与 macOS 均暴露不含密钥的 API 校验状态；界面运行环境提示显示实际客户端版本或明确错误。
- API 校验、接口结构和服务端临时错误不再把账号误标为“失效”；只有明确的 access token 鉴权错误才标记凭证失效。账号卡片和词库详情显示真实错误。
- 永久结构不兼容进入 `unsupported`，界面显示“当前版本暂不支持”并停止引导用户重复点击；临时权限和运行错误仍保留重试入口。
- UI、错误状态与 1.8.2 版本收口后，最终 `npm run check` 通过 168 项、跳过 1 项；另以真实
  2.8.0 `app.asar` 运行签名提取测试 17/17 通过。
- 版本整理时发现 Rust package 仍停留在 1.8.0，已将 package、lock、Tauri 配置、Windows 程序集、
  构建脚本、README 与发行测试统一为 1.8.2；最终 arm64 Lite 构建日志确认 Rust package 为 1.8.2。
- 最终 arm64 Lite DMG 通过 release smoke test 并已安装到 `/Applications/Typeless 工具集.app`；
  `/api/env` 返回 1.8.2、Tauri/Lite/arm64、本机 Node 22.23.2 和可用的 `mac_2.8.0` API 校验。
- 候选启动后自动在正式 Typeless 上完成弹窗维护：状态为 patched，完整性提供方为
  `macos-info-plist`，正式 App 严格代码签名验证通过并已正常运行。两个账号的额度、个性化、词库、
  快照和引导状态均正常；App staging 和安装临时 App 已清理。
- 本次补丁改变了 Typeless 的 ad-hoc 代码身份，旧辅助功能和麦克风记录已成功清除。需要用户按系统
  提示为 Typeless 本体重新授权并完成一次实际听写，作为发布前最后人工验收。
- 收尾发现旧事务会永久保留完整 `Typeless.app`，本机历史副本已累计约 10GB。现改为补丁或官方更新
  期间只保留单次回滚副本；新 App 通过签名校验并确认启动后立即删除，成功恢复旧 App 后同样清理，
  只有回滚本身失败时才保留副本供人工恢复。该修复不引入多版本留存策略。
- 新的 1.8.2 arm64 Lite DMG 已通过 headless release smoke test 并安装；安装后的 Tauri/Lite、外部
  Node 22.23.2、`mac_2.8.0` API 校验、弹窗状态、新手引导、严格代码签名和 Typeless 进程均正常。
